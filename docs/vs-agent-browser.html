chrome-relay vs agent-browser

Hands-on tested 2026-06-11, both tools on the same machine, same page (Hacker News front page). agent-browser v0.27.x — Vercel Labs, 35.8k stars, launched Jan 2026 as a weekend project by one engineer (Chris Tate). Blue boxes explain the jargon — click them.

agent-browser gives your agent a browser.
chrome-relay gives your agent your browser.

The two architectures

agent-browser downloads its own copy of Chrome and runs it invisibly in the background. It's a sandbox: fresh profile, no logins, no extensions, no history. Fast and disposable — built for tests, scraping, CI.

chrome-relay attaches to the Chrome you're already using — real cookies, real logins, real extensions — and operates tabs in the background without stealing your focus while you keep working.

agent-browser Rust CLI → unix socket → daemon (stays running) → CDP → its own hidden Chrome
chrome-relay Node CLI → localhost HTTP → native messaging host → extension → CDP → your real Chrome
What is CDP?

Chrome DevTools Protocol — the wire protocol behind Chrome's DevTools panel. Anything DevTools can do (click, type, screenshot, read the network tab, run JS) is available as commands over this protocol. Both tools speak CDP at the bottom; everything above it is just plumbing to reach a Chrome instance.

What is a "native messaging host"? Why does chrome-relay need an extension?

Chrome extensions can't talk to your terminal directly — they're sandboxed. Native messaging is Chrome's official escape hatch: the extension is allowed to launch and exchange messages with one whitelisted program on your machine (the "host"). chrome-relay's CLI talks HTTP to that host, the host pipes messages to the extension, and the extension uses chrome.debugger (CDP from inside Chrome) to drive tabs.

Why bother with this longer chain? Because it's the only way to attach to an already-running Chrome. The direct route (a debug port) requires relaunching Chrome with a special flag — killing your session — and leaves the port open to any process on your machine. The extension route attaches to the live browser, with Chrome's own permission system in front of it.

What's a daemon / unix socket, and why is agent-browser fast?

A daemon is a background process that starts once and stays alive. agent-browser's first command boots it; every later command just sends a message to it over a unix socket (a local file-based pipe, faster than HTTP). So a command costs ~30ms instead of booting anything. The CLI itself is a compiled Rust binary, which starts in ~0ms — versus Node, which pays ~110ms of startup tax per command. That's why chrome-relay commands take 150–260ms: mostly Node booting, not actual work.

What is "Chrome for Testing"?

A special Chrome build Google ships for automation — no auto-update, no sync, no signing into Google. agent-browser downloads it on install (~171MB, you saw this). The catch: anti-bot systems like Cloudflare fingerprint it and block it, and it never has your logins.

The live proof

Happened during testing

I opened news.ycombinator.com in both. agent-browser's sandboxed Chrome saw the logged-out page — with a login link. chrome-relay saw no login link at all, and my scripted click on it "failed"… because you're logged into HN in your real Chrome. Same URL, two different realities.

Every page behind auth — dashboards, admin panels, Gmail, Stripe, anything Cloudflare-protected — only exists in chrome-relay's world. That's the moat. Don't compete on "a browser for agents" (Playwright and agent-browser own that). Compete on "your browser, agent-operable."

Why do kilobytes matter? (the token economy)

Every byte a CLI prints lands in the agent's context window — the model's working memory, which is limited and billed per token (~4 characters each). A 61 KB page read costs ~15,000 tokens; agent-browser's 13.5 KB costs ~3,400. Over a 50-step browsing session, that's the difference between the agent staying sharp and the agent drowning in its own page dumps. Token efficiency isn't a nice-to-have — it's the product axis these tools compete on.

1. Their action loop is closed. Ours is broken.

agent-browser's whole workflow is three commands:

agent-browser snapshot -i     # see the page: every element gets a ref like @e3
agent-browser click @e3       # act using that ref
agent-browser snapshot -i     # re-look after the page changed

chrome-relay's read also assigns refs (ref_1, ref_2…) — but no command accepts them. They're decoration. To click something, the agent must copy back a brittle 100-character CSS selector like:

tr:nth-of-type(1) > td:nth-of-type(2) > span:nth-of-type(1) > b:nth-of-type(1) > a:nth-of-type(1)

…or run a different snapshot command (ax) to get a different kind of id, usable only by a different click command (click-ax). Two snapshot systems, two id spaces, refs that go nowhere.

What's an accessibility tree? And what's a backendDOMNodeId?

The accessibility tree is the simplified view of a page that Chrome builds for screen readers: just roles and labels ("button: Submit", "link: Hacker News"), with all the layout divs stripped out. It's the cheapest honest description of a page, which is why both tools use it for snapshots. chrome-relay's ax command reads it via CDP; agent-browser's snapshot renders its own version of it as text.

A backendDOMNodeId is Chrome's internal serial number for a DOM element. It's a better element handle than a CSS selector (no string matching, survives most page reshuffles) — chrome-relay already uses these under the hood for click-ax. The fix is to put a friendly ref_N alias on top and accept it everywhere.

2. Output format is the whole token game

agent-browser prints one short text line per element:

- link "Hacker News" [ref=e102]
- cell "1." [ref=e10]

chrome-relay prints pretty-printed JSON where the same element costs ~300 bytes: a bounds object with 4 coordinates, that giant selector string, verbose key names, indentation whitespace. That's the entire 4.5× gap — it's a formatting problem, not an architecture problem. None of bounds/selector is needed in the default view once refs are actionable.

3. Features they have that agents actually use

  • wait — wait for a selector, for text to appear, for a URL pattern, for the network to go quiet. chrome-relay has nothing; agents sleep blindly and re-read.
  • get text|value|attr|count — grab one value without paying for a full page snapshot.
  • find role button click — semantic locators ("the button labeled X") as a fallback when refs are stale.
  • diff snapshot — print only what changed since the last look. ~100 tokens instead of re-reading the page.
  • batch — several commands in one process launch.
  • skills get core — the agent instruction manual ships inside the CLI, so it's always version-matched. Their installable skill file is deliberately tiny: it just says "run agent-browser skills get core". Smart distribution.
  • screenshot --annotate — numbered labels drawn on the image that match snapshot refs. Vision + refs in one artifact.

Where the hype cracks

  • Ref staleness is their #1 real complaint. Their refs die the moment the page changes. GitHub issue #1351: a team migrating 150 e2e tests measured +65% more LLM calls than with Playwright MCP, because ~30% of all turns were just re-snapshots. The per-snapshot token win got eaten by turn count.
  • "100% Rust" is a distribution story, not a product story. Rust matters for them — it removes the Node dependency from their installer. It does not make snapshots smaller or loops shorter. An independent source-read found their Rust accessibility renderer is actually noisier than the Node/Playwright code they deleted. Rewriting chrome-relay in Rust would be vibes: the extension is necessarily JavaScript, and the real costs are output tokens and round-trips, not binary startup.
  • Reception is lopsided. 35.8k GitHub stars but near-zero Hacker News traction (top submission: 2 points), 517 open issues at 5 months old, Vercel Labs (not core product), one dominant contributor.
  • The sandbox is the weakness. Blocked by Cloudflare fingerprinting, no real auth, loses device settings between opens. One field test scored it 6.1/10 vs Playwright's 8.0 for actual test-writing.
What is MCP, and why does neither tool want it?

Model Context Protocol — the standard for plugging tools into agents as structured function calls (like the Playwright MCP server). The problem: every MCP tool's schema gets injected into the agent's context on every single turn — measured at ~13–17k tokens of pure overhead for browser-tool servers. A CLI costs zero until the moment it's used, and the agent already knows how to run shell commands. agent-browser's explicit no-MCP stance is correct, and chrome-relay should keep it: CLI + a skill file is the right interface.

What to build, in order

  1. Compact text snapshot as the default output One line per element: ref_3 [link] "Hacker News". JSON moves behind --json; bounds and selectors behind flags. ~5–10× token cut for the cost of a print function. Biggest win, zero architecture change.
  2. Close the ref loop click ref_3, fill ref_5 "x", hover ref_2 — the extension keeps a per-tab map of ref → backendDOMNodeId from the last snapshot. Kills the selector-echo entirely. Bonus: backendDOMNodeIds survive page changes that kill agent-browser's refs — you can beat them at their own #1 weakness.
  3. Unify read and ax into one snapshot command One command, one ref space. Today's split is pure confusion tax — and full ax output (337 KB) is actually bigger than read because it walks the whole tree unfiltered.
  4. wait For a selector / text / URL pattern / network-quiet. Cheap via CDP, removes the sleep-and-re-read loop.
  5. Snapshot diff read --diff returns only elements that changed since the last snapshot of that tab. The extension already keeps per-tab state (console/network ring buffers prove the pattern). This turns their #1 weakness into your headline feature.
  6. find — semantic locators find role button "Save" click. Deterministic, cheap, better foundation than the planned natural-language resolver.
  7. get one-liners get text|value|attr|count <sel> — one value, no full snapshot.
  8. batch Multiple commands per invocation — also amortizes Node's 110ms startup.
  9. skills get core in the CLI Version-matched agent guide shipped inside the binary; thin SKILL.md that defers to it.
  10. Error hygiene Seen live: element-not-found surfaced as internal_error with a raw JS stack trace instead of the structured element_not_found code that already exists. Older handlers bypass the error system.

Non-goals: Rust rewrite, headless/sandbox mode, cloud browser providers, an MCP server.

agent-browser is what your agent uses to browse the web.
chrome-relay is what your agent uses to operate your web — the logged-in, real-profile Chrome you're already sitting in, without taking it over.

Ship items 1–4 and the token story equalizes. The auth story was never a contest.
