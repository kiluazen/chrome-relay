# Codebase impact: what the adoption spec does to chrome-relay's internals

Companion to `agent-browser-adoption-spec.md`. That doc says what to build; this one answers a different question: **does building it leave the codebase better or worse?** Where do overlaps collapse, which primitives get sharper, and where could this genuinely rot the codebase if done carelessly.

Baseline for scale: the whole extension+protocol+program surface is ~3,560 lines across ~20 files. This is a small, tidy codebase. Every change below is judged against keeping it that way.

---

## 1. The headline: this is a consolidation disguised as features

chrome-relay today has **three element-identity systems**, none of them good enough to be the only one:

1. **CSS selector strings** — what `click`/`fill`/`hover` accept. Generated by `makeSelector` in `page-actions.ts:47-80`, a 33-line nth-of-type path builder that produces `tr:nth-of-type(1) > td:nth-of-type(2) > ...`. Brittle, huge, and the single biggest line-item in the token bill.
2. **Decorative `ref_N`** — emitted by `readPageSnapshot` (`page-actions.ts:188`), accepted by nothing. Dead weight on the wire.
3. **backendDOMNodeId** — used by `ax`/`click-ax`, the only identity that survives DOM reshuffles, locked behind a separate snapshot command and a separate click command.

And **two snapshot implementations** that don't know about each other:

- `readPageSnapshot` (`page-actions.ts`, in-page DOM walk, 287-line file) — produces identity #1 and #2
- the AX walker (`a11y.ts`, 288 lines, CDP-side) — produces identity #3

And **two click handlers** (`chrome_click_element`, `chrome_click_ax`) that are 80% the same resolution logic with different entry points.

The spec collapses all of it: **one snapshot builder** (AX tree + cursor sweep), **one identity primitive** (the RefMap entry: `{tabId, backendNodeId, role, name, nth}`), **one click-resolution funnel** with three entry forms (ref / CSS / coords). Identity systems 3 → 1. Snapshot paths 2 → 1. Click paths 2 → 1.

### The deletion ledger

| dies | why it can die |
|---|---|
| `makeSelector` + the whole selector-path concept in output | existed only because refs weren't actionable. Refs are the fix, not a workaround |
| decorative `ref_N` generation | replaced by real refs |
| `chrome_click_ax` as a separate tool | folds into the unified resolver |
| `bounds` on every element in default output | coordinate data moves behind a flag; agents click refs |
| `read`/`ax` handlers as parallel code | become day-one aliases onto the new handler (see §4b), removed on a written version |
| the "ax is ~30× smaller" doc claim | measured false on full output (337 KB > 93 KB); the new snapshot makes the claim unnecessary |

What gets **ported, not deleted**: `stateFor` (`page-actions.ts:117-169`). State-on-interactive-elements was a deliberate design call (boundaries.md §2.8 — `read -i` answers "what does the form currently say?", halving form-verification round-trips). The new text format keeps it for cheaper: `[checked]` attrs and `: value` suffixes instead of a JSON state object.

Net lines: roughly flat (the cursor sweep and renderer are new code of similar size to what dies). Net *concepts*: cut by more than half. That's the trade you want.

## 2. The verb model: 20 tools become 5 primitives

Today the tool surface reads as a flat list of 20. After the spec it factors cleanly:

```
target    (tab | workspace | group | ref-implied)     ← exists, gains ref-implication
snapshot  (see the page, get handles)                 ← unified
act       (click/fill/type/hover/keys × ref|css|xy)   ← unified resolution
wait      (until selector/text/url/load/fn)           ← new primitive
observe   (screenshot, console, network, screencast)  ← unchanged
```

This matters beyond aesthetics: **future features stop being new tools and start being compositions.** `get text @e3` is snapshot scoped to one node. `snapshot --diff` is snapshot plus stored text. A future `find` is a snapshot query. When features compose out of primitives, the marginal feature costs a handler stanza, not a new subsystem — that's the definition of the primitives being right.

The agent-facing skill doc inherits the same structure: teach 5 verbs, not 20+ tools. What's clearer for the maintainer is what's clearer for the agent — same artifact.

## 3. Existing patterns the plan confirms (build-on, not bolt-on)

- **Per-tab state in the service worker** — RefMap is the *third* instance of a pattern that already exists twice: `console-buffer.ts` (225 lines) and `network-buffer.ts` (443 lines) both keep capped per-tab state with tab-close cleanup. RefMap should mirror their shape, and if the third instance makes the abstraction obvious, extract the shared per-tab-registry helper all three use. The pattern was proven before this plan needed it.
- **`tools.ts` is 34 lines of name→handler dispatch** — which is why `batch` is nearly free: it's a loop over a map that already exists. A feature that drops in this cheaply is evidence the dispatcher was built right; nothing about batch fights the architecture.
- **The closed `RelayError` code set** — `stale_ref` slots in as one new member. Change 8 (sweeping plain `throw new Error` out of handlers — every throw in `page-actions.ts` is one, and one was observed live surfacing as `internal_error` with a raw JS stack) isn't new direction; it *finishes* item 2 of `code-quality-hardening.md`, already on the roadmap.
- **Protocol package as single source of truth** — the new tool schemas, the `@ref` argument grammar, and the text renderer all land in `packages/protocol`. The renderer especially: putting it there makes the snapshot text format a tested contract shared by CLI and tests, instead of an accident of string concatenation in the CLI.

## 4. Where this could be a disaster (the honest section)

### a. RefMap is the first state where staleness causes a *wrong action*

The existing per-tab state (console/network buffers) fails soft: stale buffer → missing log lines. A stale ref fails **hard**: the agent clicks the wrong element, in the user's real browser, possibly in the wrong tab. This is the most dangerous code in the plan.

Guardrails that must hold:
- One module owns the map. No handler touches ref state except through it.
- Every action on a ref re-verifies through CDP before dispatching (`DOM.getBoxModel` on the cached backendNodeId — the fast path *is* the verification; it cannot be skipped as an optimization).
- Hydrated-from-`chrome.storage.session` state is never trusted blind — it exists to survive SW restarts, and still goes through the same CDP verification on first use.
- Wrong-tab clicks are structurally impossible: refs carry tabId, and a contradicting `--tab` is `target_conflict` (spec Change 2). This rule is what makes the global map safe; drop it and the feature is a footgun.

### b. Deprecated aliases that never die

The disaster mode: `read`/`ax` "kept for one release" become permanent, and the codebase carries three snapshot surfaces forever — strictly worse than before the plan. Guardrails:
- The old handler code is **deleted on day one**. Aliases are thin mappings onto the new snapshot handler that print a `deprecated` notice — they do not preserve the old output format, because keeping the old format means keeping the old code.
- The removal version is written in the spec, and `release-notes.ts` (the mechanism exists) announces it.

### c. The renderer's home decides whether format changes are cheap

If text rendering lives in the CLI, every format tweak touches extension JSON + protocol types + CLI string code, and printed text can drift from wire data. Guardrail: renderer in `packages/protocol`, golden-file tested; the CLI is `print(renderSnapshot(data))` and nothing else.

### d. `wait` meets a four-layer timeout stack

CLI read timeout, HTTP server, native-host bridge, and the handler's own poll loop each have a deadline. A `wait` that outlives its caller leaves a zombie poller in the extension burning a CDP attach. Guardrail: the handler caps `--timeout` strictly below the transport timeout, and all the numbers live in `packages/protocol/src/limits.ts` — which already exists for exactly this kind of constant. No magic numbers in handlers.

### e. `batch` vs the 1 MB native-messaging frame

Each command's response fits; a batch of snapshots aggregated into one response may not. Guardrail: size-check the accumulated response, fail with `invalid_arguments` naming the offending index. (Longer term, per-command response streaming — out of scope, noted, not silently ignored.)

### f. Net surface still grows

+`snapshot` +`wait` +`get` +`batch` +`skills` against −`read` −`ax` −`click-ax` is +2 net once deletions execute. The plan only deserves the "consolidation" label if the deletions actually happen — which is why they're written as acceptance criteria and versioned removals, not intentions.

## 5. The test story gets materially better

- **Golden-file tests become possible.** Today snapshot output is a JSON blob nobody asserts on in full. A stable text format is the natural golden artifact: `render(fixtureTree) === golden.txt`. First real regression net for output format — which is now a product surface (it's what agents bill tokens on).
- **A live regression page with teeth.** The autark.sh app measured 37 cursor-pointer div-soup clickables invisible to pure AX filtering — it's the named acceptance test for the sweep. Cloudflare dash (0 div-soup, measured) is the control.
- **Errors become assertable.** Post-Change-8, tests assert `error.code === "stale_ref"` instead of regexing stack strings. The existing test suites (`page-actions.test.ts`, `protocol.test.ts`, `program.test.ts`) get stronger assertions for free.

## 6. Verdict

The plan passes the codebase test because its biggest feature (actionable refs) is also its biggest cleanup (one identity system instead of three). The features the spec borrows from agent-browser land on patterns this codebase already proved — per-tab state, closed error codes, dispatch-as-data, protocol as SSOT — rather than importing agent-browser's architecture (daemon, Rust, owned browser), which would have been the actual disaster.

The two failure modes worth fearing are not architectural but disciplinary: aliases that never die (§4b) and ref state acted on without CDP re-verification (§4a). Both are cheap to prevent now and expensive to fix later; both are encoded as hard rules above. Hold those two lines and the codebase comes out the other side smaller in concepts, better tested, and with primitives that the next five features compose from instead of adding to.
